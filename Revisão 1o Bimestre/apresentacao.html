Modelos de Serviço: IaaS, PaaS, SaaS

  MAIS ABSTRATO
  ┌─────────────────────────────────────────┐
  │  SaaS  │ Gmail, Office 365, Salesforce   │ → cliente usa
  ├─────────────────────────────────────────┤
  │  PaaS  │ App Engine, Elastic Beanstalk   │ → cliente desenvolve
  ├─────────────────────────────────────────┤
  │  IaaS  │ EC2, Azure VMs, redes virtuais  │ → cliente gerencia SO
  └─────────────────────────────────────────┘
  MENOS ABSTRATO

Regra de ouro: quanto mais alto na pirâmide, menos o cliente gerencia.

  • IaaS: cliente controla SO, apps, dados, rede virtual
  • PaaS: cliente controla apps e dados
  • SaaS: cliente controla apenas seus dados e configurações de usuário

Responsabilidade Compartilhada + CapEx vs. OpEx

🏢 Provedor — segurança DA nuvem

  • Hardware físico e datacenters
  • Rede física global
  • Hipervisores e virtualização
  • Energia e refrigeração

👤 Cliente — segurança NA nuvem

  • IAM e controle de acesso
  • Configuração de firewalls
  • Criptografia dos dados
  • Patching de SO (em IaaS)
CapEx: grande investimento inicial em hardware depreciável
OpEx: pagamento contínuo pelo consumo real (pay-as-you-go) → reduz barreira de entrada, alinha custo ao negócio

Princípios de Arquitetura em Nuvem

💥 Design para falha

Todo componente falhará. Projete assumindo isso. Elimine pontos únicos de falha (SPOF).

🔗 Desacoplamento

Componentes independentes via APIs, filas e eventos. Falha de um não derruba o sistema.

📈 Escalabilidade

Horizontal (scale out): + instâncias → ilimitado
Vertical (scale up): + recursos → tem limite

⚙️ Automação

Infraestrutura via código (IaC). Ambientes reproduzíveis, consistentes, sem configuração manual.

Tolerância a Falhas — Alta Disponibilidade

Zonas de Disponibilidade (AZs): datacenters físicos independentes dentro de uma região, interconectados por fibra de baixíssima latência (< 2ms).

PadrãoComo funciona
Multi-AZRecursos replicados em 2+ AZs — elimina SPOF
Failover automáticoBanco promove réplica em < 60s em caso de falha
Load Balancer cross-AZDistribui tráfego apenas entre AZs saudáveis
Auto ScalingRepõe instâncias com falha automaticamente
Regra de ouro: se existe um único componente cuja falha derruba o sistema, há um SPOF a corrigir.

Segurança Inicial e Gestão de Custos

🔐 Segurança em camadas

  • IAM com menor privilégio
  • Criptografia em trânsito (TLS)
  • Criptografia em repouso (AES-256)
  • Logs de auditoria desde o início

💰 Gestão de custos

  • Monitorar utilização (evitar ocioso)
  • Rightsizing desde o provisionamento
  • Entender o que gera cobrança:
  • Computação + storage + egress
"A nuvem não é mais barata por padrão — é mais barata quando bem gerenciada."

Nuvem Híbrida

NIST: composição de 2+ infraestruturas distintas interligadas por tecnologia que permite portabilidade de dados e aplicações.
PadrãoComo funciona
Cloud BurstingPico excede capacidade local → transborda para nuvem pública
Tiered DeploymentDados sensíveis on-prem; apps web na nuvem pública
Disaster RecoveryDR na nuvem pública, ativado só em falha do site primário
Modernização gradualLegado on-prem + novos serviços nativos na nuvem

Conectividade: VPN site-to-site (IPsec) Direct Connect / ExpressRoute

Multi-cloud e a Diferença Fundamental

☁️ Nuvem Híbrida

  • Privada/on-premises + pública
  • Ambientes de naturezas diferentes
  • Conectividade dedicada
  • Foco: modernização gradual, compliance, DR

🌐 Multi-cloud

  • Dois ou mais provedores públicos
  • Ex.: AWS + Azure + GCP
  • Foco: evitar lock-in, best-of-breed
  • ⚠️ Atenção ao egress cost
Ferramentas habilitadoras: Terraform (IaC agnóstico) · Kubernetes (portabilidade) · Azure Arc / Google Anthos

Redes Virtuais — VPC: Componentes Fundamentais

ComponenteFunção
Bloco CIDREspaço de endereços da VPC (ex.: 10.0.0.0/16 = 65.536 IPs)
Sub-rede públicaTabela de rotas com 0.0.0.0/0 → IGW
Sub-rede privadaSem rota para IGW (isolada da internet)
Internet Gateway (IGW)Comunicação bidirecional VPC ↔ internet
NAT GatewaySaída (egress) das instâncias privadas — bloqueia entrada
Route TableDefine destino do tráfego por sub-rede
IGW vs. NAT: IGW = porta bidirecional (pública). NAT = saída apenas (privada).

Security Groups vs. NACLs

CaracterísticaSecurity GroupNACL
Nível de atuaçãoInstância (ENI)Sub-rede
EstadoStateful — resposta automáticaStateless — regras entrada + saída
Tipo de regrasApenas ALLOWALLOW e DENY
ProcessamentoTodas as regras avaliadasOrdem numérica (para no 1º match)
Defesa em profundidade: SG (granular por instância) + NACL (amplo por sub-rede) = duas barreiras independentes. Se uma camada for comprometida, a outra ainda protege.

Arquitetura Multi-Tier com VPC

           INTERNET
               │
   ┌───────────▼──────────┐  Sub-rede PÚBLICA   → IGW
   │    Load Balancer      │  SG: 80/443 de 0.0.0.0/0
   └───────────┬──────────┘
               │
   ┌───────────▼──────────┐  Sub-rede PRIVADA
   │    Servidores App     │  SG: app-port apenas do SG do LB
   └───────────┬──────────┘
               │
   ┌───────────▼──────────┐  Sub-rede PRIVADA ISOLADA
   │    Database (RDS)     │  SG: 3306/5432 apenas do SG da App
   └──────────────────────┘

Cada camada replicada em 2 AZs → alta disponibilidade. Cada SG só aceita tráfego da camada imediatamente anterior.

Three-Tier e Microsserviços vs. Monolito

Three-Tier: apresentação (CDN + LB) → aplicação (Auto Scaling) → dados (RDS Multi-AZ). Cada camada escala e falha independentemente.

📦 Monolito

  • Uma unidade de deploy
  • Simples inicialmente
  • Escala uniforme (tudo ou nada)
  • ✅ Ideal para MVP e equipe pequena

🧩 Microsserviços

  • Deploy e escala por serviço
  • Database per service
  • Complexidade operacional alta
  • ✅ Ideal para escala e equipes grandes
Regra prática: comece monolítico, evolua para microsserviços quando a escala exigir.

Serverless, Event-Driven e Escalabilidade

⚡ Serverless

  • Zero gerenciamento de servidores
  • Custo zero quando idle
  • ⚠️ Cold start na 1ª invocação
  • ⚠️ Máx. 15min por execução (Lambda)

📡 Event-Driven

  • Componentes via eventos, não chamadas
  • Pub/Sub, Event Streaming, Event Bus
  • Desacoplamento total
  • Resiliência e auditabilidade
TipoComoLimite
Scale Up (vertical)Aumenta recursos da instânciaMaior tipo disponível
Scale Out (horizontal)Adiciona instânciasIlimitado (teórico)
Auto ScalingAutomatiza scale out/inConfigurável por política

Exercício · Objetiva

Questão Modelo — Aula 6

Uma instância em sub-rede privada precisa baixar atualizações da internet, mas não pode ser acessada diretamente de fora. Qual componente viabiliza esse cenário?

  • A) Internet Gateway colocado diretamente na sub-rede privada
  • B) NAT Gateway, posicionado na sub-rede pública, com rota 0.0.0.0/0 → nat-xxx na route table privada
  • C) Security Group com regra ALLOW para 0.0.0.0/0 na porta 80
  • D) NACL com regra DENY para todo tráfego de entrada
  • E) VPC Peering com outra VPC que possui Internet Gateway
Resposta: B — O NAT Gateway traduz o IP privado da instância para IP público, permitindo saída, mas bloqueia conexões de entrada iniciadas externamente. O IGW na sub-rede pública fornece o acesso à internet ao NAT.

Exercício · Dissertativa

Questão Modelo — Aulas 4, 6 e 7

Cenário: Um hospital deseja migrar para a nuvem. Prontuários eletrônicos exigem máxima segurança e controle regulatório (LGPD). O sistema de agendamento de consultas precisa suportar picos de acesso.

Para responder: (a) qual modelo de implantação para cada sistema? (b) como organizar a VPC com sub-redes e gateways? (c) qual pilar do Well-Architected é mais crítico para cada?

Diretrizes:
(a) Prontuários → Privada (controle + LGPD) · Agendamentos → Pública (elasticidade) · Combinação = Híbrida
(b) Sub-rede privada isolada p/ prontuários · sub-rede privada p/ app · sub-rede pública p/ LB · NAT para saída
(c) Segurança (prontuários) + Confiabilidade (agendamentos)
