❌ Sem Load Balancer

  • Ponto único de falha
  • Capacidade limitada
  • Downtime em manutenção
  • Degradação com carga

✅ Com Load Balancer

  • Redundância
  • Escalabilidade horizontal

ALB: Roteamento por Conteúdo

/api/*       → Target Group: API Servers
/images/*    → Target Group: Image Servers
/*           → Target Group: Web Servers

Host: admin.site.com → Target Group: Admin

Regras baseadas em:

  • Path da URL
  • Host header (domínio)
  • HTTP headers customizados
  • Query strings
  • IP de origem

Health Checks

Fluxo:

  1. LB envia verificação periódica (HTTP GET /health)
  2. Target responde 200 = saudável ✅
  3. Falhas consecutivas → marcado unhealthy ❌
  4. Removido do pool → tráfego redistribuído
  5. Recuperou → volta ao pool automaticamente
Parâmetros: Interval: 30s | Timeout: 5s | Unhealthy: 2 falhas | Healthy: 3 sucessos

Cache Hit vs. Cache Miss

⚡ Cache Hit (rápido)

Usuário → Edge (tem cache) → Resposta direta
Latência: ~5-20ms

🔄 Cache Miss (primeira vez)

Usuário → Edge (não tem) → Origem → Armazena → Responde
Latência: ~100-200ms (apenas na 1ª vez)
Métrica-chave: Hit Ratio > 90% = CDN bem configurada

Arquitetura Integrada: CDN + LB

Usuário → CDN (Edge)
              │
    Hit? → Resposta direta ⚡ (~80-95% tráfego)
              │
    Miss? → Load Balancer → ASG → BD
Resultado:
  • CDN absorve 80-95% do tráfego estático
  • LB processa apenas tráfego dinâmico
  • Servidores com carga reduzida
  • Custo otimizado (egress CDN mais barato)

Resumo

Pontos-chave desta aula:
  • Load Balancer: distribui tráfego, garante HA e escalabilidade
  • ALB (L7) para HTTP; NLB (L4) para performance extrema
  • Health checks removem targets com falha automaticamente
  • CDN reduz latência via edge locations próximas
  • Cache hit = instantâneo; cache miss = busca na origem
  • CDN + LB = combinação essencial para produção
