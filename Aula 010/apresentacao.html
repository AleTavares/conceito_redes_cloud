AbordagemReativo (thresholds)Investigativo
Exemplo"CPU está alta?""Por que ESTA req falhou?"

Os Três Pilares

📊 1. Métricas

Valores numéricos ao longo do tempo. Baixo custo, ideais para dashboards e alertas. Ex: CPU, latência, req/s.

📝 2. Logs

Registros de eventos discretos com contexto. Alto detalhamento (prefira JSON). Ex: requisição HTTP, exceção, login.

🔗 3. Traces

Caminho completo de uma requisição. Identificam gargalos em microsserviços. Ex: requisição atravessando 5 serviços.

Amazon CloudWatch

Serviço central de observabilidade da AWS:

  • Metrics: Coleta de EC2, RDS, Lambda, ELB + customizadas
  • Logs: Centralização + busca via Logs Insights
  • Alarms: Dispara ações (SNS, Auto Scaling, Lambda)
  • Dashboards: Painéis visuais consolidados
EC2, RDS, Lambda, ALB → CloudWatch → Dashboards
                            ↓
                      Alarms → Ações automáticas

Distributed Tracing (X-Ray)

O problema: Uma requisição atravessa 10+ microsserviços. Onde está a lentidão?

Requisição
  → [API Gateway 5ms]
  → [Auth 12ms]
  → [Pedidos 8ms]
  → [Pagamento 450ms ⚠️]
  → [DB 15ms]
  • Cada segmento = um span
  • Conjunto de spans = um trace
  • Trace ID único conecta tudo
  • Service map ilustra dependências

SLIs, SLOs e Error Budgets

TermoDefiniçãoExemplo
SLIIndicador medido% req < 200ms
SLOMeta desejada99,9% em 30 dias
SLAContrato com clienteMulta se < 99,5%
Error Budget:
  • SLO 99,9% → orçamento de 0,1% de falhas
  • Orçamento disponível → priorizar features
  • Orçamento esgotado → priorizar estabilidade

Boas Práticas

  1. 🔧 Instrumentar desde o início do desenvolvimento
  2. 📋 Logs estruturados (JSON com campos consistentes)
  3. 🔗 Correlacionar os 3 pilares via trace_id
  4. 🎯 Centralizar tudo (nunca logs isolados por servidor)
  5. 📊 Definir SLOs realistas (baseados no usuário)
  6. 🔕 Reduzir ruído — cada alerta deve ser acionável
  7. 💾 Retenção adequada (custo vs. auditoria)
